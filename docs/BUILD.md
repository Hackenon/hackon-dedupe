# Building the Windows client

The app normally runs with `python app.py`. To hand someone a double-clickable
app, build it with **PyInstaller**.

Packaged builds keep read-only files (templates, assets, docs) inside the bundle,
and write user data (settings, results, logs, the downloaded ffprobe) to
`%APPDATA%\HackOn` — so the app works even when installed in a read-only location.
Running from source is unchanged: your data stays in the project folder.

## Quick build (one command)

On Windows, in the project folder with the venv active:

```
python tools/build_exe.py            # build dist/HackOn/HackOn.exe
python tools/build_exe.py --clean    # wipe build/ + dist/ first
python tools/build_exe.py --release  # build, then zip + SHA-256 for a release
```

It installs PyInstaller if needed and builds from `hackon-dedupe.spec`. The manual
steps below are the same thing by hand.

## Build (Windows)

In the project folder, with the venv active:

```
pip install pyinstaller
pyinstaller hackon-dedupe.spec
```

Output: **`dist\HackOn\HackOn.exe`**. Double-click it — it starts the local server
and opens your browser at http://127.0.0.1:5000, just like `python app.py`.

To share it for testing, zip the whole **`dist\HackOn\`** folder (the exe needs the
files next to it).

## Installer (Windows, Inno Setup)

The onedir build is a folder (`HackOn.exe` + `_internal\`). To hand people a single
file, wrap it in an installer:

```
python tools/build_exe.py --installer                 # build + compile HackOn-Setup.exe
python tools/build_exe.py --installer --version 1.3.0  # override the version for this build
```

This needs **Inno Setup 7** (free): https://jrsoftware.org/isdl.php. The tool finds
`ISCC.exe` on PATH or in its default install folder and compiles `installer\hackon.iss`.

The version comes from the **`VERSION`** file at the project root (bump it there; `--version` overrides for a one-off). It installs for all users into **`C:\Program Files\HackOn Systems\HackOn Photo & Video DeDupe`** (admin/UAC), with a Start Menu shortcut and uninstaller.

Output: **`HackOn-Setup.exe`** at the project root, plus its SHA-256 in `SHA256SUMS.txt`.
It installs for all users into `C:\Program Files\HackOn Systems\HackOn Photo & Video DeDupe`
(prompts for admin/UAC),
adds a Start Menu shortcut and an uninstaller, and offers an optional desktop icon.
User data still lives in `%APPDATA%\HackOn`, so the Program Files location stays
read-only at runtime and uninstalling leaves a tester's settings/results untouched.

The wizard is themed in the CRT green-phosphor style: the welcome/finish panel and
the inner-page banner use `installer/assets/wizard-*.png`, regenerated by
`python tools/make_installer_art.py` (Pillow). Re-run that after a palette or logo change. A
`[Code]` block in `installer/hackon.iss` recolors the inner page bodies green-on-black to match; if ISCC rejects a control class in it, delete that branch and the image theming still applies.

Note: unsigned, so Windows SmartScreen still warns "unknown publisher" until the exe
is code-signed (Authenticode). The checksum only proves the download wasn't corrupted.

## Notes
- First launch creates `%APPDATA%\HackOn\` for settings, results, logs and the
  ffprobe download, so each tester starts with a clean setup (your dev data is
  untouched).
- The build keeps a console window so you can watch the server log and any errors
  while testing. For a quieter release build, set `console=False` in
  `hackon-dedupe.spec`.
- App icon: `assets/icon.ico` (generated by `python tools/make_app_icon.py`) is
  embedded in `HackOn.exe` via the spec and used for the installer
  (`SetupIconFile`); shortcuts inherit the exe's icon. Re-run the generator after
  a logo change.
- If PyInstaller reports a missing module at runtime, add it to `hiddenimports`
  in the spec and rebuild. (scipy / numpy / Pillow / imagehash are handled by
  PyInstaller's built-in hooks.)
- This is a onedir test build. A signed Windows installer and the Mac `.app` are
  the next packaging steps on the plan.

## Releasing a build (with checksums)

1. **Build and zip** (onedir is a folder, so you ship a zip):
   ```powershell
   pyinstaller hackon-dedupe.spec
   Compress-Archive -Path dist\HackOn\* -DestinationPath HackOn-Setup.zip -Force
   ```
   (Zip the *contents* of `dist\HackOn\` so `HackOn.exe` and `_internal\` sit at the
   zip root.)

2. **Checksum** — publish SHA-256 (the one that matters; MD5/SHA-1 are broken for
   security, fine only for spotting a corrupted download):
   ```powershell
   Get-FileHash .\HackOn-Setup.zip -Algorithm SHA256 | Format-List Algorithm,Hash,Path | Out-File SHA256SUMS.txt
   ```

3. **Publish** on GitHub Releases (your site + `DEFAULT_REPO` already point at
   `/releases`): create a release, attach `HackOn-Setup.zip` and `SHA256SUMS.txt`,
   and paste the SHA-256 into the notes. Repeat the hash + link on the website.

4. **Users verify** with:
   ```powershell
   Get-FileHash .\HackOn-Setup.zip -Algorithm SHA256      # Windows
   # macOS/Linux:  shasum -a 256 HackOn-Setup.zip
   ```

A checksum proves the download wasn't corrupted or swapped in transit — not that the
app is safe or that you built it (the user is trusting the hash on your page). Code
signing (Authenticode) is the real trust upgrade; until then Windows SmartScreen
warns "unknown publisher" regardless of checksums.
